# 0010: The API is an OAuth authorization server for the remote MCP servers

Status: accepted (2026-11-16). Replaces the "Later" section of ADR 0004.

## Context

The MCP endpoints (`/mcp/ops`, `/mcp/admin`) accepted only an hl-crm-db API key as a bearer token. Clients that connect by OAuth (claude.ai custom connectors, ChatGPT connectors, Cursor's web agents) couldn't connect. People sign-in and browser sessions now exist (ADR 0009), so a person can sign in and approve an app.

The MCP authorization specification (revisions 2025-06-18, 2025-11-25 and 2026-07-28) makes the MCP server an OAuth 2.1 resource server: it publishes Protected Resource Metadata (RFC 9728), accepts only tokens issued for itself (RFC 8707 audience), never passes a client's token through to another service, and answers 401 and 403 with `WWW-Authenticate` challenges. The authorization server must do authorization code with PKCE S256, take `resource` on both requests, return `iss` (RFC 9207), and register clients through Client ID Metadata Documents, with Dynamic Client Registration (RFC 7591) deprecated but still used by many clients. Claude's documentation lists the 2025-03-26, 2025-06-18 and 2025-11-25 authorization specifications, so clients of all those revisions have to work.

The installed MCP SDK (1.32.2) speaks protocol revisions up to 2025-11-25. Revision 2026-07-28 removes the initialize handshake and sessions, carries the version and client capabilities in every request's `_meta` (mirrored into `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers), adds `server/discover`, and adds `resultType` and cache hints to results.

## Decision

**The API process is the authorization server, on `PUBLIC_URL`.** It serves `/.well-known/oauth-authorization-server` (and the same document at `/.well-known/openid-configuration`), `/oauth/authorize`, `/oauth/token`, `/oauth/revoke` and `/oauth/register`. The `issuer` is `PUBLIC_URL`'s origin. The MCP process stays a resource server with no database credentials. OAuth is off until `MCP_PUBLIC_URL` is set; setting it without `PUBLIC_URL` or `MCP_SERVICE_SECRET` stops both processes from starting.

**Resources and scopes.** The two resources are `<MCP_PUBLIC_URL>/mcp/ops` and `<MCP_PUBLIC_URL>/mcp/admin`. Scopes are the API key scopes: `ops:read`, `ops:write`, `restricted:read`, `admin`, with one hierarchy: `ops:write` implies `ops:read`. The ops resource takes the three non-admin scopes; the admin resource also takes `admin` and needs it. A token's effective access is computed exactly as for a key, on every request: the member's current role ∩ what the granted scopes unlock, within the scopes the workspace currently allows, with the role's object and field rules. A person can't grant a scope their role can't use (`ops:write` falls back to `ops:read` for a reader).

**Opaque tokens, not JWTs.** Access tokens (`hlcrm_oat_…`), refresh tokens (`hlcrm_ort_…`) and authorization codes (`hlcrm_oac_…`) are 256 random bits stored as SHA-256, found by a narrow lookup policy before the tenant is known, like API keys and sessions. Every use re-reads the token, its grant, the member and the workspace settings, so revoking, disabling, a role change or the workspace switch applies on the next request, and nothing has to be verified offline. A JWT would let a revoked token work until it expires and would add key management for no gain: the only party that ever checks these tokens is this API. The prefixes let secret scanners find them and let a request tell them from API keys.

**How the MCP process uses a token without passing it through.** Two designs were considered:

- (a) The MCP process sends the client's token to the API together with a server-to-server credential, `MCP_SERVICE_SECRET`, shared by the two processes. The API accepts an OAuth access token only when that secret is present and correct (compared in constant time), and fixes the request's surface from the token's resource: the MCP process states which endpoint it is serving (`X-Hlcrm-Surface`), and a token for the other resource is invalid there.
- (b) Token exchange (RFC 8693): the MCP process trades the MCP token for a short-lived API token at the authorization server and calls the API with that.

We chose (a). The API stays the only place that checks anything: audience, expiry, revocation, the member, the role, the workspace. A stolen MCP token is useless against `/v1` directly (it is refused without the secret, whoever presents it, the client it was issued to included). The token never reaches any service other than the one that issued it and enforces it. (b) would add a second kind of token that does work against `/v1` for its lifetime, either a cache of exchanged tokens in the MCP process (state it doesn't have today) or an extra round trip per request, and a second place where lifetimes and revocation have to agree. The cost of (a) is a secret to configure for both processes; Compose and `init-env.sh` pass it, and OAuth refuses to start without it, or with one that doesn't look random (fewer than 32 characters, fewer than 16 different ones unless it is 64 or more hex digits, or a shorter string repeated). Wrong secrets are counted per client address (30 a minute) and checked before the secret is compared, apart from failed API keys: the MCP process passes callers' keys on, and their failures must never stop it presenting tokens. API keys on the MCP endpoints are unchanged: a bearer value shaped like an hl-crm-db key takes the old path and never carries the secret.

**One workspace and one member per token.** Approval happens in a session, which belongs to one workspace; the grant records that member and workspace. To connect another workspace, a person signs in to it and approves again.

**Consent, every time.** `/oauth/authorize` validates everything (client, redirect URI, PKCE, response type, resource, duplicates) before it shows anything. Without a session it sends the browser to the ordinary sign-in page with the request as `return_to` (that limit rose from 512 to 2,048 characters for this) and starts over when it comes back. The consent page opens with the site the approval will be sent to (that is the site being trusted), names the app and says how far that name can be trusted (a metadata document published at the client ID URL's host, or a self-registration that proves nothing), warns plainly when a document on one host sends the approval to another (allowed, but its name then proves nothing about the receiving site), warns when the app receives the result on the person's own computer (loopback), lists what it could do in plain words and what wasn't granted and why, and is shown for every authorization request: consent is never remembered, so a new client, a new redirect host or a wider scope always asks. Approving `admin` needs a sign-in in the last 10 minutes. The decision is a form post with the session's CSRF token and the same Origin and Sec-Fetch-Site checks as every form (ADR 0009); the page can't be framed and runs no script, and its `form-action` includes the redirect origin because browsers apply it to the redirect.

**Errors before consent are shown, not redirected.** An unknown client or an unregistered redirect URI gets an error page that never points at it. Other problems (missing PKCE, an unknown `resource`, `prompt=none`) carry `error`, `state` and `iss` back to the app's redirect URI, but on a page with a link the person follows, not as an automatic redirect: since anyone can register a client or publish a metadata document, an automatic error redirect would make this origin an open redirector to whatever site they chose (RFC 9700 §4.11.2). After the person approves or cancels, the response is a redirect.

**Codes live 60 seconds.** A code is redeemed by the client's back end as soon as the browser reaches the redirect URI; a minute covers slow networks and keeps a leaked code short-lived. A code is single use, bound to the client, the exact redirect URI, the PKCE challenge, the resource, the scopes and the consenting session (which must still be live when the code is redeemed). A second use revokes the grant the first use created.

**Refresh tokens rotate on every use, and reuse ends the grant.** Each refresh issues a new access token and a new refresh token and marks the old refresh token used; presenting a used one again revokes the whole grant (RFC 9700 §4.14.2). This is strict: two refreshes racing with the same token end the connection, and the person approves again. A refresh can narrow the scopes of the new access token, never widen them or move it to another resource. The `scope` a token response reports is what the new token can use now (the grant's scopes, or those asked for, within what the workspace allows and the member's role can use), not what was granted. Defaults: access tokens 60 minutes, refresh tokens 30 days unused, a grant at most 180 days (settings `OAUTH_ACCESS_TOKEN_MINUTES`, `OAUTH_REFRESH_TOKEN_DAYS`, `OAUTH_GRANT_MAX_DAYS`). Connecting the same app to the same server again replaces the earlier grant.

**Client registration, three ways in, no allowlist.**

- *Client ID Metadata Documents* (preferred by the 2026-07-28 spec): a `client_id` that is an https URL with a path, on port 443, is fetched through `lib/outbound.ts` (https only, private, loopback, link-local and metadata addresses refused, internal names refused, DNS pinned, no redirects, 32 KB, and one 5-second deadline for DNS and the request together; before, each had its own timeout, so a fetch could take 10 seconds). The document must have `client_id` equal to the URL exactly, a `client_name` and 1 to 20 acceptable `redirect_uris`, and no client secret. It is cached in `oauth_clients` per its `Cache-Control` between 5 minutes and a day. The fetch happens on the authorization request, because the redirect URI must be checked against the document before anything is shown. Key sets (`jwks_uri`, also port 443) are fetched under the same guard.

  Anyone can name any URL, so the fetcher is built so that no unauthenticated caller can stop a client this server already knows from working (see the limits table in `docs/mcp/oauth.md`). A *known* URL (a cached client's document, a key set fetched before or on a cached client's own host) is refetched under its host's own budget (60 a minute) and its own pool of fetch slots (16, at most 4 per registrable domain). A URL *never seen* is charged to the caller's address (20 a minute, at most 2 at once) and to its registrable domain (30 a minute, at most 4 at once), from a separate pool of 32 slots, so bogus client IDs on a real client's host use up neither its budget nor its slots. A failed document is remembered per URL for 5 minutes (at most 5,000), so repeats cost nothing. A cached copy past its cache life is served at once while it is fetched again in the background (stale while revalidate), for at most a day past its cache life, checked in code; once such a refresh has failed, a new authorization needs a fresh copy, while the token and revocation endpoints keep using the cached one so an app's host being down doesn't end its connections. A refreshed document always replaces its cached copy. When 10,000 unexpired documents are cached, a new one makes room (expired copies first, then the least recently used), and one host's documents fill at most 500 places (a new one replaces that host's least recently used). Key sets are cached in memory for 5 minutes; an assertion naming a key the set lacks fetches it again at most once a minute per set, and the last good set keeps verifying (up to a day) when a fetch fails or is refused. A refused document or key set gets the same `invalid_client` whatever went wrong; the reason (status, not JSON, DNS) is only logged, so this server can't be used to probe other hosts.
- *Dynamic Client Registration*: unauthenticated by design, so it is limited to 20 an hour per client address (an IPv6 /64 counts as one address) and 200 an hour per IPv6 /48. Past 300 an hour server-wide an error is logged (`oauth_registration_surge`), but nothing is refused: a hard server-wide figure let about 15 addresses stop every new self-registering connection. Live registrations are capped at 10,000; at the cap, the oldest registration that never led to a token and is more than 15 minutes old makes room (one that issued tokens never does), and only if there is none is the request refused. A registration that never leads to a token lapses after 24 hours (each token issue keeps it alive as long as its refresh tokens can be). `application_type` is honoured when sent (`web`: https, non-loopback redirect URIs only; `native`: loopback http too); when it is left out (clients written for earlier revisions), it is inferred by the same rule: any loopback redirect URI makes the client `native`. Metadata documents follow the same rule. Registered clients are public (`token_endpoint_auth_method: none`).
- Pre-registration doesn't exist; there is nothing to configure per client.

Redirect URIs must be https, or plain http to `localhost`, `127.0.0.1` or `[::1]`, and match a registered one exactly, except that a loopback URI may use another port (RFC 8252 §7.3). Custom URI schemes are refused.

**Client authentication.** Public clients send `client_id` and nothing else; they are protected by PKCE. A metadata-document client may declare `private_key_jwt` with a `jwks_uri` (ChatGPT's document does); it must then sign a client assertion (RFC 7523) with a key from that set, whose issuer and subject are its `client_id`, whose audience is this server, which expires within 10 minutes and whose `jti` is accepted once (`oauth_assertions`). No client secrets are issued or accepted; a `Basic` header is refused.

**Data model (migration 014).** `oauth_clients` and `oauth_assertions` exist before any workspace is known, so they have no tenant; their policies show a request only the client or assertion it names, plus deliberately flagged counting, making room under the caps (any cached document, or a registration that never issued a token) and cleanup. `oauth_codes`, `oauth_grants` and `oauth_tokens` are tenant tables with forced RLS; codes and tokens add select-only lookup policies by hash, like `api_keys.key_lookup`. Grants keep a copy of the client's name and kind and the redirect URI the person saw, so the record of a consent doesn't change when a client does. The audit surface CHECK gains `oauth` (token endpoint events) and the idempotency credential CHECK gains `oauth`.

**Revocation everywhere it belongs.** Disabling a member revokes their grants and tokens in the same transaction as their keys and sessions. "Sign out everywhere" (`POST /v1/auth/sessions/revoke-others`, and an admin's `POST /v1/members/{id}/sessions/revoke`) also disconnects their apps, because those apps act as the member. A password change doesn't: it ends other sessions, but an app connected deliberately keeps working, as API keys do. A member disconnects an app at `/auth/apps` or `DELETE /v1/auth/apps/{id}`; an admin with `members:manage` lists and disconnects a member's apps (`GET /v1/apps?member=…`, `DELETE /v1/apps/{id}`, `crm apps`) under the owner and permission-superset rules used for sessions. The access review lists each member's apps.

**Per workspace, the owner decides.** `PATCH /v1/workspace/sign-in` takes `oauth_apps` (on by default) and `oauth_scopes` (which scopes apps may be granted; by default all four; allowing `ops:write` allows `ops:read`, as for tokens). Turning apps off revokes every grant in the workspace at once; narrowing the scopes applies to existing tokens on their next request, and turning apps back on restores nothing.

**Everything is audited, nothing secret is.** In the member's workspace: `oauth.consent_granted`, `oauth.consent_denied` (surface `web`), `oauth.token_issued`, `oauth.token_refreshed`, `oauth.token_revoked`, `oauth.code_reuse_detected`, `oauth.refresh_reuse_detected` (surface `oauth`), `oauth.grant_revoked`, and `workspace.sign_in_changed`. Work done with a token is audited on `ops-mcp` or `admin-mcp` with the member as actor and `details.oauth_grant` and `details.oauth_client`. A registration happens before any workspace is known, so it is logged (`oauth_client_registered`), and each consent entry names the client. No token, code or verifier is stored or logged.

**Both MCP revisions on the same endpoints.** Requests without 2026-07-28 metadata go to the SDK as before (initialize, then requests). A request whose `MCP-Protocol-Version` is `2026-07-28`, or whose `_meta` carries a protocol version, is handled as 2026-07-28: the header must equal `_meta`'s version and `Mcp-Method` (and `Mcp-Name` where it applies, including its base64 form) must match the body, or it is a 400 `HeaderMismatch` (-32020); another version gets `UnsupportedProtocolVersionError` (-32022) listing the supported ones; `server/discover` is answered from what the SDK reports; removed methods (`initialize`, `ping`, `logging/setLevel`) and `subscriptions/listen` (these servers have no change notifications) are 404 -32601; anything else runs through the SDK as a 2025-11-25 request and its result gets `resultType: "complete"`, `serverInfo` in `_meta`, and on lists `ttlMs` and `cacheScope: "private"`.

**Challenges.** Without a usable token, each endpoint answers 401 with `WWW-Authenticate: Bearer resource_metadata="<MCP_PUBLIC_URL>/.well-known/oauth-protected-resource/mcp/<name>", scope="…"` (`ops:read ops:write` for ops, `admin ops:read` for admin), plus `error="invalid_token"` for a bad one; with a token whose effective scopes can't use the endpoint, 403 with `error="insufficient_scope"`. Tokens are never read from a query string. The MCP process limits failed OAuth bearer values to 30 a minute per client address (the API trusts it through the secret), except for a token that worked in the last five minutes and hasn't been refused since: the first 401 from the API takes that pass away.

**The grant is the credential.** Requests made with any of a grant's tokens share one identity: one rate-limit bucket (`oauth:<grant>`, the same 20 a second with bursts of 200 as a key), one idempotency namespace (`credential = 'oauth'`, `credential_id` the grant), and `details.oauth_grant` in the audit log. Refreshing doesn't start a new budget, and two connections of one member don't share one. Anything that binds to a credential (a confirm token, an idempotency record) binds to the grant. Combined with sessions and the write side, `credential(ctx)` in `core/context.ts` returns `oauth:<grant>` for an OAuth context, so the heavy-request gate (2 per grant), route costs and confirm tokens key on the grant like the rate limit does; a member's connected apps together also hold at most 4 heavy requests at once (`HEAVY_LIMITS.perMemberApps`), because approving another app is one click.

**Availability.** Hosted clients (Claude, ChatGPT) use one `client_id` for all their users, from a few addresses, so the limits are designed so that no unauthenticated party can cut such a client off. Nothing shared by every user of a client is charged for a request that proves nothing (a public `client_id` is public): at the token endpoint, requests are limited per address (600 a minute), requests that find no code or refresh token (or name an unknown client) per client ID and address (300 a minute), and only requests whose code or refresh token exists, or whose assertion verified, per client and workspace (1,200 a minute). At the authorization endpoint, the per-address limit (120 per 15 minutes) is the control on floods; the per-client one (2,000 per 15 minutes) counts only a signed-in member's request whose redirect URI checked out, per client and workspace. The OAuth limit windows are kept in memory apart from the sign-in ones, so churning them can't push a sign-in lockout out, and under pressure expired and unblocked windows are dropped first.

## Consequences

- claude.ai custom connectors, ChatGPT connectors, Cursor and Claude Code can in principle connect by signing in and approving. None of this was tried against a real client (see `docs/mcp/oauth.md`).
- The API process now makes outbound requests on behalf of unauthenticated callers (metadata documents and key sets), bounded as above. A slow host holds a fetch slot for at most 5 seconds, and a flood of slow URLs is held to a few slots per caller and per domain, in a pool apart from known clients'.
- A cached document can be used for an authorization up to a day past its cache life while it is fetched again; a client that removes a redirect URI from its document sees that take effect after one more request (or immediately, if the refresh fails).
- Limits are in memory per process, like the sign-in limits; several API processes multiply them.
- Hosted clients refresh from a few addresses for all their users, so the token endpoint's limits are generous (600 a minute per address, 1,200 per client and workspace once a code or refresh token is found). A member could still use up their own workspace's share for a client by refreshing in a loop; that costs them, not other workspaces.
- Registrable domains are approximated (the last two labels, three under a two-letter country code with a short second level) without a public suffix list.

## Not built

- Remembered consent (every authorization asks).
- Pre-registered or confidential clients with secrets; `private_key_jwt` for registered clients; mutual TLS; DPoP or other sender-constrained tokens.
- Token introspection (RFC 7662) for third parties; the MCP process is the only consumer, through the API.
- Custom URI scheme redirects (some desktop clients use them).
- OAuth sign-in for the `crm` CLI.
- A shared (cross-process) rate limiter, and refreshing metadata documents before they are needed (a stale one is refreshed in the background when next used).
- `subscriptions/listen` and the 2026-07-28 extensions (tasks, MRTR input requests): the tools don't need them.
